How the SnakeByte bot works, piece by piece

A walk through bot.cpp and its tools as of v1.11 / v1.13: the simulator, the search, the evaluation, the value net, what was learned from the top players' own games, and the way every change is measured, with the numbers found along the way.

328 → 3Legend rank of 394, legacy bot → v1.11
36.04arena score (35.54 on a second run), from 17.91; the first two are at 38.3
40k–60ksimulated turns per 38 ms turn on CodinGame (all snakes moved)
1,848arena games replayed exactly from their seed and moves

The bot is one C++ file of about 1,900 lines with its local tools; the submission is that file without the tools and comments plus the net's weights as text, 93k characters. This page follows the data through it, then the tools around it:

The rules that matter

Two players, up to four snakes each, on a side-view grid of platforms. Every snake moves one cell per turn, all at once, and gravity pulls down any snake that rests on nothing. The longest total body wins. Several rules are only visible in the referee's Java source, and the simulator has to get every one of them right:

  • Order within a turn: all moves, then eats, then beheadings, then falls.
  • The tail moves first. A cell a tail just left is free, unless that snake ate this turn (then the tail stays).
  • Eating comes before beheading. Two heads entering the same apple both grow, then both lose their head.
  • Three parts or fewer (counted with the new head) and a collision removes the whole snake. A longer one only loses the head.
  • The facing is not stored. It is head minus neck, recomputed every turn. A backward command is ignored.
  • Outside the grid is empty space, not wall. A snake dies out there only when every part is at y ≥ height + 1, and only right after a fall step.
  • Ties are broken by "losses", the parts lost to beheadings and collision deaths.

Board: a 64 × 64 byte array

The grid is at most 44 × 24, but snakes may hang off its edges, so the model adds room around it: 10 columns left, 20 rows on top, and the rest to the right and below. One byte per cell.

ValueNameMeaning
0EMPTYfree
1APPLEpower source: solid for falls, eaten by a head
2WALLplatform
3VOIDedge of the model: a head that enters it is beheaded, nothing rests on it
4 + iSNAKE + ia body part of snake i

The order of the values is chosen so the two hot tests are one comparison each:

occ[c] >= WALL      // a head here collides: wall, void or any body
occ[c] <  WALL      // free to enter: empty or apple
Why a ring of VOID. With it, no move and no fall ever needs a bounds check: any step off the model lands on a cell that already says "stop". It is the one place the model differs from the game, where a snake could wander more than 9 columns outside the grid. The search never wants to, and no opponent has in a checked game.
The top margin was 8 rows until v1.1. Two arena games had simulator mismatches (11 in one, 1 in the other): a snake standing on other snakes had climbed above the model. The model is now 64 rows with 20 above the grid, and the mismatches are gone.

Snake and state

struct Snake: a ring buffer

struct Snake {
    uint16_t b[128];              // cells; b[h] is the head
    uint8_t h, len, alive, sup;   // sup: parts with a wall or an apple right below
    uint8_t f;                    // facing: 0 up, 1 right, 2 down, 3 left
    int head()      { return b[h]; }
    int part(int i) { return b[(h - i) & 127]; }        // 0 = head
    int tail()      { return b[(h - len + 1) & 127]; }
};

The facing f is cached instead of recomputed from head minus neck on every selection. It is written when a head advances. A beheaded snake does not advance, so it keeps the old value, which is exactly "old head minus old neck": the referee's rule, for free.

struct State

struct State {
    uint8_t occ[4096];     // the board
    Snake s[8];            // player 0's snakes first, then player 1's
    int napples, turn;
    int losses[2];         // the tie-break
    int len[2], alive[2];  // total body parts and live snakes per player
};                         // 6,200 bytes

len, alive and napples are updated in place by every move, so the end-of-game test and the score cost nothing:

bool terminal() { return napples == 0 || alive[0] == 0 || alive[1] == 0 || turn >= 200; }

A whole state is copied once per search iteration. At 6.2 kB that copy is 3–4% of the search time, so the state was kept simple instead of adding undo logic.

One turn: State::step

Three passes over the snakes, in the referee's order.

Pass 1: move, and release the tail

for each live snake i:
    nh[i]  = head + DELTA[mv[i]];
    eat[i] = occ[nh[i]] == APPLE && len < 127;       // the ring buffer holds 128
    if (!eat[i]) {
        t = tail;
        sup -= (occ[t + 64] is WALL or APPLE);   // the tail was resting on something
        occ[t] = EMPTY;  len--;
    }

Tails are cleared before any collision test. That one ordering gives the rule "a cell a tail just left is free" with no special case, including a snake chasing its own tail.

Pass 2: who collides

col[i] = occ[nh[i]] >= WALL;                     // wall, void, any body (own included)
for j != i:  if (nh[j] == nh[i]) col[i] = true;   // two heads, same cell

All collisions are decided on the same picture of the board, before any new head is written, because the referee resolves them simultaneously. Other snakes' old heads are still in occ: they are necks now, and still solid.

Pass 3: apply

if (!col[i]) {                       // normal move
    h = (h + 1) & 127;  b[h] = nh[i];  f = mv[i];  len++;
    occ[nh[i]] = SNAKE + i;
    if (eat[i]) napples--, len[owner]++, unsupport(nh[i]);
    sup += (occ[nh[i] + 64] is WALL or APPLE);
} else {
    if (occ[nh[i]] == APPLE) remove the apple;        // eaten by every head on it
    size = len + 1;                                  // with the new head
    if (size <= 3) die: clear the body, losses += size;
    else           behead: losses += 1;             // nothing to undo: the head was never written
}
The beheading costs nothing. The new head is only written for snakes that survive. A beheaded snake "moved forward and lost its head", which leaves it exactly where pass 1 left it: the old body, one tail cell shorter.

Falls

The referee's rule: a snake is grounded if any part is directly above a wall, an apple or a grounded snake. Every other snake drops one row, together, and the test repeats. That loop is in the source as falls(), kept as the reference. It was 47% of the search time, because falling is not rare: a snake climbing straight up falls back one row every single turn. Counted later on two positions: 95–98% of simulated turns have at least one snake in the air, 2.5–4.3 snakes per turn, and nearly all of them really drop, by one row on average. In the trees the snakes climb at random and come down again, so the fall code is the common path.

Trick 1: support counters

sup counts the parts of a snake that have a wall or an apple directly below. Three events change it, and step handles all three as it goes:

  • the tail leaves a cell above a wall or apple: −1
  • the head arrives above one: +1
  • an apple is eaten: the part sitting on it, of whichever snake, loses its support (unsupport): −1
unsigned air = 0;
for each live snake i:  if (!s[i].sup) air |= 1 << i;
if (air) fastFalls(air);        // usually skipped for most snakes

If every snake has sup > 0, nothing can fall and the turn is done. Otherwise only the snakes in air are looked at.

Trick 2: fastFalls, drop straight to the landing row

Snakes in the air fall in lockstep, so they never block one another. That means the drop of one airborne snake is simply the distance to the first cell, under any of its parts, that is neither empty nor part of another airborne snake.

for (;;) {
    for each snake i in air:
        d[i] = min over its parts of (free cells straight below);
               // a part with its own body right below is skipped: the lower part decides
        if (d[i] == 0) { air -= i;  restart; }   // rests on a grounded snake: it is ground now
        lim[i] = rows until all of it is below the grid;
    m = smallest d[i] or lim[i];
    clear all airborne snakes from occ;
    shift each by m rows;   those with lim[i] == m are out of the game;
    write them back;
    those with d[i] == m have landed: recount sup, air -= i;
    if (!air) return;
}

Compared with the reference loop, which rescans all eight snakes for every single row of every fall, this touches only the airborne snakes and usually runs once.

Why "restart" on a drop of 0. A snake resting on a snake that is itself in the air must fall with it. A snake resting on a grounded one is grounded. Removing it from air changes what counts as transparent for the others, so they are measured again.

Proving it exact

Fast code against reference code

Build the bot and the referee twice, once with -DSLOWFALL (the referee's loop, no shortcuts). With a fixed number of iterations and fixed seeds the search is deterministic, so both builds must play the same games move for move. 80 games with 8 snakes each: identical results. The same test covered the support counters and the cached facing, and it is the gate for every later change that must not alter play: the reordered reach table and the bit-row engine experiment were both checked this way (same scores and lengths of 40 games).

The simulator against CodinGame: resync

The input never says what the opponent played. Each turn the bot takes the previous position, its own moves, and tries every combination of opponent moves, three per snake, at most 81:

for each combination c:
    State t = prevS;
    t.step(my moves + combination c);
    if (sameState(t, cur)) {             // every body, cell for cell, and the apple count
        cur.losses = t.losses;           // losses are not in the input either
        playedMv = these moves;
        return true;
    }
return false;                            // the simulator disagrees with the game

One pass does three jobs: it proves the simulator matched the referee on that turn, it recovers the opponent's moves, and it carries the tie-break counters forward. A failure is counted in the status line the bot prints every turn (desync N) and tagged DS on a move, which shows in arena battle logs. Since the taller board model: 0 failures.

Search: Smitsimax

Eight snakes moving at once is 3⁸ = 6,561 joint moves per turn, too many for a normal tree. Smitsimax gives each snake its own tree over its own moves and runs them all in one shared simulation.

struct Node

struct Node {
    float   w[4];    // sum of values per move, from my point of view
    float   n[4];    // visits per move; float so SSE can load it directly
    int32_t ch[4];   // child node per move, 0 = none yet
    int32_t N;       // visits of this node
};                   // 52 bytes, in one array of 1.5M allocated once

Nodes come from a bump allocator (newNode: clear 52 bytes, return the next index). The pool is not cleared between turns: resetting the counter to 1 is the whole "free". Index 0 means "no node".

validMask: prune suicide

For the snake's three non-backward directions, a move is kept if the target cell is empty or an apple, or if it is the tail of some snake (which will have moved away). If nothing is left, the snake goes straight. Without this, random moves into walls drown the statistics, as one mid-Legend post-mortem reported.

selectMove: UCB with no branches

The formula per move is q = ±w/n + C·sqrt(ln N / n), with the sign flipped for the opponent's snakes. Written as a loop with ifs it was 42% of the search time on CodinGame: the branches depend on random data and mispredict. The x86 version computes all four moves at once and has no data-dependent branch:

e = C * sqrtLog[N];                              // sqrt(ln N) from a table of 65,536 floats
n = load(nd.n);
q = load(nd.w) * sign * rcp(n)  +  e * rsqrt(n);    // SSE approximate 1/n and 1/sqrt(n)
q = blend(q, 1e6 + random byte, n == 0);         // unvisited: huge, in random order
q = blend(-1e9, q, maskTab[mask]);               // not a valid move: never
m = horizontal max of q;
return ctz(movemask(q == m));                    // position of the maximum
  • rcp and rsqrt are the 12-bit approximate instructions: about 4 cycles each instead of ~15–20 for a division or a square root, and UCB does not need more precision.
  • Unvisited moves get 10⁶ plus a random byte, so they win against any visited move and tie-break randomly, with no separate "expand" code path.
  • maskTab is a 16-entry table of ready-made SSE masks, indexed by the 4-bit valid-move mask.

After the change selection is 24–31% of the time. ARM builds (the local Mac) use the plain loop with the same logic.

The loop: search

for (;;) {
    every 16 iterations: stop if the clock passed the budget;
    depth = 3 + iters/250   (first 1000 iterations)   then +1 per 1000;
    State S = root;                                   // the 6.2 kB copy
    for (d = 0; d < depth && !S.terminal(); d++) {
        for each live snake i:
            mask = validMask(S, i);
            m    = selectMove(pool[cur[i]], mask, sign of owner);
            remember (cur[i], m);
            cur[i] = child of cur[i] by m, created if missing;
        S.step(all moves);
        sum += length difference;                     // for the "eat sooner" term
    }
    raw = evaluate(S, ..., own);                      // once, at the end
    val[i] = squash((raw ± 0.64·own[i]) / 8.55);      // one value per snake, see below
    for every remembered (node, m) of snake i:  w[m] += val[i];  n[m]++;  N++;
}
play, for each of my snakes, the most visited move at its root;
  • Progressive depth. The first iterations are shallow (depth 3), so every snake's first moves get sampled before anything deep is tried. By the end of a turn the depth is 11–14. The schedule is the one in _H3R0_'s post-mortem. Starting deeper looked like +135 Elo at 1,000 iterations per move and was −3 in real time: depth must be tested at the real budget.
  • There is no rollout. The whole line is inside the trees; below the last node of a tree the snake's first visit is a random valid move. The line stops at depth and the evaluation takes over.
  • The clock is read every 16 iterations, not every one: reading it costs about as much as a quarter of an iteration.
  • Budget. 38 ms counted from the first input line of the turn, 850 ms on the first turn (the reach tables take 30–200 ms of it and stop at 700 ms whatever happens). It was 44 ms until CodinGame's machines started freezing the process for 2–30 ms in the middle of a turn: five of 35 battles were lost on time in one evening, with the same code that had lost one in 159 that morning.
  • A prior on the moves. Since v1.10 the selection adds a bias that fades with the visits of a move; it comes from the top players' own games and has its own section.
  • Exploration constant 0.735. 0.35 → 0.7 was +61 Elo; the last digits are from the SPSA run.

Per-snake credit

The largest single gain of the project. In plain Smitsimax every tree receives the same value. But that value mostly reflects what the other seven snakes happened to do in that simulation, so each tree is learning from noise.

own[i] = (length of snake i now − at the root) − its distance cost;     // dead: −(its length at the root)

val[i] = squash((raw ± EV_SELF·own[i]) / EV_K);   // + for my snakes, − for theirs (they minimise)
...
node.w[m] += val[i];                              // each tree gets its own snake's value

Every snake still sees the shared result, plus an extra share of what it did itself. Measured against the same bot without it:

Weight of own[i]0.5124
Elo vs weight 0 (100 games each, ± 75–95)+269+288+205+173

squash is a rational approximation of tanh (x(27+x²)/(27+9x²), clamped at ±3). Eight values per iteration made the real tanh worth replacing. Taking weight away from the shared value instead (0.25 / 0.5 of it) loses 89 / 31 Elo: the snakes still need the common goal.

Evaluation

The distance cost must stay near one apple. When a snake eats the last apple it can reach, its "nearest apple" jumps to something far away or out of reach. If that jump costs more than the apple was worth, the evaluation goes down for eating, and the snake refuses to eat. Larger distance weights lost for exactly this reason (−89 Elo at 0.2 per cell) until the cost was capped.

Reach tables: distances that know gravity

Board dumps of lost games showed the real problem with v1.0: the snakes sat still. Most apples hang in the air, a snake of length 3 cannot reach one four rows up, and a plain shortest-path distance pointed straight at it. The opponent ate 19 apples in the first 24 turns; we ate 12.

What a snake can reach depends on where its body lies, and the body lies on the last cells of the head's path. So the tables are a search over (cell, run), where run counts the cells the head has entered since the last supported cell (a free cell with a wall right below). A snake of length L holds itself up while run ≤ L − 1:

Step of the headNew run
into a supported cell0
downunchanged (hanging or falling, the head goes down either way)
sideways or uprun + 1, allowed while ≤ L − 1
sideways at run L − 1the whole snake drops one row: the head ends on the cell below
into the apple itselfalways allowed: it is eaten before the fall, and growing keeps the tail where it was

bfsGravity(a) runs this search backwards from apple a, once for every length 3 to 12 (longer snakes use 12), and writes gd[length][run][cell][apple]: moves to the apple, one byte, 255 = cannot get there. At a leaf, reachIdx finds where the snake is in the tables: its length index, and its current run (parts in front of its first part that rests on a wall or an apple).

  • The apple index is the innermost one. A leaf asks for every apple from one (length, run, cell), so those answers sit next to each other in memory. With the apple outermost each lookup was a cache miss, and the evaluation was 23% of the search time; reordered, 14%, with identical play.
  • Size. apples × 10 lengths × 12 runs × 4,096 cells: 22 MB for 46 apples, built in 100–180 ms on CodinGame's first turn.
  • Three models were tried before this one. "Never fall, and charge the snake's current stretch to every run" (−73 to −382: a standing snake saw nothing as reachable). "Head within L − 1 of any supported cell" (static; wrong where the body cannot lie on that cell, which left snakes hopping under apples all game). The path model beat it by +51 ± 45.
Standing on another snake counts (v1.8). When a snake's place in the tables is read (reachIdx), a part resting on another snake's body ends the run like a wall does. Both top bots treat snakes this way; ours used to count such a snake as hanging in the air.
Only walls are support in the tables (v1.3). Until v1.2 the apples of the first turn counted too. But the tables are built once, and an apple is gone when it is eaten: the table kept walking over a support that no longer existed. In a lost game against sZoom a length-3 snake in a pit was told for 80 turns that an apple was 9 moves away. In the simulation itself apples still hold snakes up, exactly as in the game; only the precomputed distances ignore them.

One pass over apples × snakes: scanApples

Everything the handcrafted terms and the net need from the tables comes out of one loop:

for each live snake i:  row[i] = GDROW(length index, run, head);   // its distances to all apples, contiguous
for each apple a still on the board:
    for each live snake i:
        v = row[i][a];
        keep the two smallest in d1[i], d2[i];   cnt[i] += (v != 255);
        m[owner] = min(m[owner], v), remember which snake;
    both 255          -> unreach++
    m[0] == m[1]      -> contested++
    otherwise         -> owned[winner]++, own[that snake]++, prox[winner] += 1 / (1 + distance)

The first version scanned twice, once for the evaluation and once for the net inputs. Merging the two brought the net build from 5.1k back to 6.2k iterations per turn on CodinGame.

Voronoi apple territory: voronoi

The reach tables know walls and gravity but not where the bodies are. A snake circled for 24 turns ten moves from an apple that sat behind an opponent's body. The second view is the opposite: it knows the bodies and ignores gravity.

A flood starts from all heads at once and spreads one cell per step over the free cells of the grid. Walls and bodies block (the tail cell does not: it will have moved). A cell belongs to the player whose flood arrives first; a cell both reach in the same step belongs to nobody and stops both. The evaluation adds 0.25 for every apple more in my territory than in theirs.

fr[y]  = free cells of row y            // one 64-bit word per row, bit = column
A[y], B[y] = my frontier, their frontier

for (step = 0; step < 32; step++) {
    for each row y:
        ea = (A[y] << 1 | A[y] >> 1 | A[y-1] | A[y+1]) & fr[y];   // one step in four directions
        eb = (B[y] << 1 | B[y] >> 1 | B[y-1] | B[y+1]) & fr[y];
        newA[y] = ea & ~eb;   newB[y] = eb & ~ea;                 // a tie belongs to nobody
        ownA[y] |= newA[y];   ownB[y] |= newB[y];
        fr[y]  &= ~(ea | eb);
    if (nothing new) break;
    swap frontiers;
}
count the apples under ownA and under ownB;
  • Bit rows. A flood step is four shifts/ORs and two masks per row for each player, over at most 24 rows. The whole flood costs 6% of a simulated turn.
  • The weight must stay small. 0.25 was +56 Elo, 0.6 was −111: with no gravity the flood happily gives away apples nobody can climb to. It is a correction next to the tables, not the main distance.
  • It needs truthful tables beside it. Walls-only tables alone: −7. Voronoi alone: +56. Both: +111 ± 66, and +143 ± 66 against v1.2 in real time.

Value net

A small net estimates "who wins from here" from the same quantities the handcrafted terms use, and its logit is added to them: raw = handcrafted + 2.18 × logit. Replacing the handcrafted value by the net alone was worse at every scale (−74 to +42); every other mix was worse than this one.

Inputs (fillFeatures)

All from the point of view of one player, all scaled to roughly 0–1. v1.3 runs the net n0b with 72 inputs: 16 about the game and 7 for each of 8 snake slots (4 per side, longest first; an empty slot is all zeros).

Global (16)Per snake slot (7)
turn; apples left; length difference; my length, their length; my losses, their losses; my live snakes, theirs; apples I own, they own (by the tables); contested apples; apples nobody reaches; grid height; sum of 1/(1+distance) over my owned apples, over theirs present; length; distance to the nearest reachable apple; to the second nearest; "has one in reach"; height of the head above the floor; apples it is the nearest of all to

The source on the main branch already has the next input set (83): the two Voronoi apple counts, a soft ownership sum, and per snake the number of apples it can reach. The net for it is being trained.

Forward pass (netForward): 72 → 96 → 32 → 1, ReLU

CodinGame compiles without -ffast-math, so the compiler may not reorder a floating-point sum, and a dot product per output unit stays scalar. The pass is written the other way round, one input at a time:

h1 = b1;
for each input k:
    if (x[k] == 0) continue;                 // empty snake slots cost nothing
    for (j = 0; j < 96; j++) h1[j] += x[k] * W1T[k][j];     // "y += a·x": vectorises as written
h2 = b2;
for each k with h1[k] > 0:                    // the ReLU: units that are off are skipped
    for (j = 0; j < 32; j++) h2[j] += h1[k] * W2T[k][j];
out = b3 + dot(W3, relu(h2));

The weights are stored transposed (netReady) so each inner loop runs along memory. The net's cost went from 54% to 12% of a simulated turn; the outputs are checked against the training side on a file of records (referee --evalcheck, values agree to the sixth decimal).

Data and training

  1. Generate (referee --gen, on Kaggle through kaggle_gen.py): the bot plays itself at fixed iterations on random maps; each snake plays a random valid move with probability 5% so the games differ. A record is the map seed, the moves of every turn and the search's own score per turn: a few hundred bytes per game. 24k games at 600 iterations, then 70k at 2,000.
  2. Export (referee --export): replay each game and write, for one position in three and for both players, the inputs plus three labels: the result (1 / ½ / 0), the final margin, the search score. Because records hold seed + moves, a change of inputs costs one export, not a new generation.
  3. Train (train.py, PyTorch on the laptop's GPU): Adam, cosine schedule, 20 epochs, batch 4,096, binary cross-entropy on a target that is half the result and half the result softened by the final margin; optionally blended with the search score.
  4. Gate like any other change (below).

Packing into the source (pack.py)

The submission must be one text file under 100k characters. Each weight is quantised to 16 bits with one scale per array and written as three characters of six bits each, starting at '0'. Two characters of that range would break a C string, the backslash and the question mark (trigraphs), so they are replaced by { and | and mapped back by dig(). 10,145 weights are 30,435 characters; the largest rounding error is 3·10⁻⁵. The packed file still compiles with -DLOCAL, so the exact text that goes to CodinGame is what plays the local gate.

Learning from the top players

By v1.8 everything measurable in self-play had been taken: six changes in a row came out level, and against sZoom and _H3R0_ we still won one game in five. Two things were missing, and neither was code: a way to measure against the players who beat us, and any knowledge of what they do differently. Both came from the same place, the logs of our own arena games.

Replaying real games exactly

A battle log holds the seed of the game and every move of both players, but not the map. Our local map generator is a port with its own random numbers. The official generator, seeded the way CodinGame's SDK seeds it (SecureRandom with the SHA1PRNG algorithm and setSeed(seed)), gives the identical map:

tools/mapdump   // 50 lines of Java around the referee's own GridMaker
tools/trace.py  // seed -> first position; + both players' moves -> every position, through our engine
tools/harvest.py // all logged battles; each replay is checked against the score line our bot printed every turn

1,848 of about 1,900 logged battles replay with no turn disagreeing. Every move sZoom and _H3R0_ made against us is a position on disk, and any turn of any game can be written out as a test position (trace.py LOG --pos T).

What the replays showed first, by counting (tools/losses.py): head-on collisions are symmetric, two a game for both sides. The difference against the top two was walls: a snake only hits a wall when it has no legal move, and ours did 0.40 times a game against them (they 0.12), losing a whole snake that way in 12% of those games.

Agreement: does our search pick the move they played?

tools/agree.py runs our search on the positions of their snakes and compares its move with the one they really made, on 14,000 decisions per player in 17 seconds. With the weights of v1.8 it agreed with _H3R0_ 60.6% of the time.

  • It behaves like a real measure: on its own it prefers the settings matches had already picked (the room cost at 1, the Voronoi at 0.25, the tuned value scale) and rejects the ones matches had rejected.
  • It found the tempo credit: +1.4 points, the largest mover among thirty switches. A quarter of all disagreements were his snake going toward its apple where ours picked a move that went away from it. Neutral in self-play, which is why it had been off; v1.9 finished at 33.75, then the best score.
  • It is not a quantity to maximise. A coordinate ascent of all weights on it gained three points of agreement, lost 90 Elo in self-play and lost to the unfitted build against _H3R0_'s own bot. One idea at a time, yes; the whole evaluation, no.

The prior in the search

These are preferences about a move, not about a position ten turns later: as evaluation terms at the leaves they changed nothing. They belong in the selection:

q[m] = mean value of m  +  C·sqrt(ln N / n[m])  +  bias[m] · K / (K + n[m])        // K = 100
  • At the root (v1.10), for every snake, ours and theirs: bias = 0.05 × (score of the move − mean score), the score from the sixteen facts (movePrefs). For their snakes it is a model of the opponent learned from his real play.
  • At every node (v1.11): the facts that need no scan (the change of table distance, target on a supported cell, straight on, up or down), weight 0.15. A few table lookups per node.
  • Not as virtual visits. Giving each move 100 imaginary visits takes the exploration away and costs agreement even with no prior at all; a bias that fades with the real visits does not.

The first gain self-play could not have found. The root prior is how the top players move; against a copy of ourselves it is worth nothing or less, and in the arena half a point. With the in-tree prior v1.11 won 73% of its battles, and against _H3R0_ five games in fourteen where it had been one in five. Wall hits against the top two fell from 0.45 to 0.14 a game.
And one the gates got wrong the other way. "Straight on" for a vertical snake is up, and up is falling back: with the priors the share of pass moves went from 18% to 40%. Charging a pass in the root prior was positive in seven Kaggle gates (2,800 games) and v1.12 finished 1.1 below v1.11 in the arena. Since then a change to the prior is one submission, and the arena is the judge.

Tuning: SPSA

After the credit term, single-parameter tests stopped finding anything: twenty in a row inside the noise. spsa.py tunes 15 parameters at once instead.

for each batch:
    δ = ±1 at random for every parameter;
    play θ + δ·step against θ − δ·step, 16 maps × both seats, 1,000 iterations per move;
    θ += lr · (score − 0.5) · δ · step;          // every parameter moves towards the side that won
    append θ to league/spsa.jsonl;                // a run continues from the last line

250 batches (8,000 games, about an hour on eight cores). The end point moved the value scale 6 → 8.55, the win bonus 4 → 8.7, the own-credit weight 1 → 0.64, the live-snake term 0 → 1.39, and nudged the rest. Tuned against untuned at the tuning budget: +10 ± 60. Against v1.2 at 3,000 iterations: +111 ± 64, and about +25 at CodinGame's budget. A tuner finds a broad region, not a peak; its value here was mostly in the parameters nobody had thought of moving together.

Protocol and resync: main

  1. Init. Read the grid into baseOcc (walls plus the VOID ring), the snake ids and owners. Allocate the node pool and fill the sqrtLog and maskTab tables.
  2. Each turn. Start the clock at the first input line. Rebuild cur from scratch: copy baseOcc, place apples, parse each body string straight into its ring buffer. Parts outside the model are cut off.
  3. Turn 1 only. initDistances: record the apple cells, mark the supported cells (bfsSupport), run bfsGravity per apple, and build the free-cell rows of the grid for the Voronoi flood (initGrid). The embedded net is decoded once before the first turn (loadEmbedded).
  4. recount. Totals per player, sup and facing of every snake.
  5. resync. Check the simulator against the game and recover the opponent's moves (above).
  6. search with what is left of the 44 ms, then print id DIRECTION for each of my live snakes, joined by ;, and one status line to stderr: iterations, depth, simulated turns, nodes, time, mismatches, losses, score, apples left. Those lines are what the arena analysis is built from.
  7. Remember the position and my moves for the next turn's resync.

The state is rebuilt from the input every turn instead of trusting the simulated one. The simulated state is only used to verify, so one bad turn can never corrupt the rest of the game.

The bit-row engine that was not kept

Since falls are the largest share, the whole board was rewritten as bit rows (tools/experiments/bitboard_engine.cpp): apples, the union of all snakes and each snake as one 64-bit word per row, and every body stored minus an offset so that a fall is one addition instead of a pass over the parts. A falling snake then costs a few word operations per row it spans, whatever its length. It played 40 games identical to the byte board. On the laptop it was exactly as fast (708 against 700 ns). On CodinGame, the same game replayed twice with each build, it was slower: 398k and 762k simulated turns in the first 850 ms against 665k and 1,013k. The byte board's loops over the parts are short, and the bit version pays on every move: two boards to update, an offset on every body read, a search for the owner of a cell.

How much is speed worth? Measured: three times the iterations is +104 Elo at 1,000 iterations per move and +63 at 4,000. At the arena's 7,000–10,000 a 1.5× faster engine is worth about +20. For scale, the per-snake credit, six lines of code, was +288, and the two evaluation fixes of v1.3 were +143. The gains of the evaluation also shrink with depth: the tuned net build was +111 at 3,000 iterations and about +25 at 7,000.

Measuring a change

Nothing goes in because it sounds right. The rule is one change, one measurement, and the result is written to docs/history.md whether it is good or bad.

tools/referee.cpp
Includes bot.cpp for the rules, so the referee and the bot cannot disagree. It adds a port of the official map generator (GridMaker.java: mirrored walls, filled air pockets, thinned walls, sunk bottom island, apples, spawns; same distribution of maps, its own random numbers) and runs two bot processes over pipes, every map with both seats. build/bot@SB_UCB_C=0.4 gives one side its own parameters. The summary line gives wins, losses, draws, Elo with its 95% interval, faults and slow turns.
fixed iterations
referee A B -g 50 -n 3000: 100 games in about three minutes on eight cores, independent of the machine's load. 100 games are ± 65 Elo, so only large effects show; anything about depth or time must be repeated in real time.
real time
The same without -n, two or three games at a time so the cores are not shared, always against the frozen binary of the live version.
tools/league.py
Freezes every submitted version (source and binary) and records head-to-head matches between versions.
tools/kaggle_match.py, kaggle_gen.py
The same matches and the self-play generation on Kaggle CPU kernels (x86 like CodinGame, two accounts): a few hundred games in parallel while the laptop does something else.
tools/gauntlet.py
Plays a source against chosen arena players through CodinGame test games and logs each result. Slow (one game a minute, 600 a day) but it is the only test against opponents that do not share our blind spots.
tools/cg.py
The CodinGame API: a test game against any player or a replay of any battle (the log with our stderr is saved), submit with the IDE mirrored, progress, leaderboard.
tools/arena.py
Archives the battles of every submission and prints the score per opponent.
tools/spsa.py, train.py, pack.py
Tuning, training and packing, described above.
What the gates cannot see. Self-play between two builds that share a fault measures nothing: the phantom-support fix alone was −7 ± 65, because both sides walked the same imaginary paths. And single arena games are close to coin flips: twelve of v1.1's lost battles, replayed with the same code, seat, map and opponent, gave nine wins. Only margins over many games mean anything.

Finding faults: one lost game, read closely

The arena logs keep our status line of every turn, so the score can be followed through each game. Over 189 battles: against everybody but the first two the margin stays near zero until the end (+0.3, +0.1, +0.2, then +1.0). Against _H3R0_ and sZoom it is 0 with three quarters of the apples left, −1.2 at half, −2.7 at a quarter, −4.9 at the end, and we lose one body part more per game than they do.

A build with #define DUMP 4 replayed on one of those games (cg.py test out/dump.cpp --replay GAME) prints the board every four turns. One game against sZoom showed three faults at once:

  1. A body part can be worth a snake. On turn 9 our C stepped into the now empty cell again, and so did X. X, at length 3, died. C lost a part and was length 3: too short to climb out of its pit, where it stayed for the remaining 190 turns. On the right their Y kept length 4, left its pit and ate nine more apples; our B, length 3, never left. Two of our four snakes ended the game at length 3. The evaluation priced "no apple in reach" at about one apple.
  2. Phantom support. It did not even see that, because the reach tables still counted the eaten apple as something to stand on, and reported an apple 9 moves away for 80 turns.
  3. Bodies are not in the tables. A length-9 snake circled for 24 turns ten moves from an apple behind an opponent's body.

Walls-only tables fixed the second and the Voronoi flood sees the third: together +143 ± 66 against v1.2, and in the arena the record against ranks 4–12 went from level to clearly ahead. The first is not solved: a flat cost for a snake with nothing in reach is −115 Elo, because a snake in the air or between apples is often without reach for a turn.

A second game, lost 41–44 after leading 39–37 with ten apples left, showed what remains. At that point their four heads were already next to seven of the ten, three of them a cluster in the top corner, reached up a wall column by a length-7 snake. Ours had been eating the nearest apple each. They take the contested and far apples first and leave the safe ones for later; the lost endgame was lost twenty turns earlier.
