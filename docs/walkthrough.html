How the SnakeByte bot works, piece by piece

A walk through bot.cpp as of v1.1: the simulator, the search, the evaluation and the tricks that make each one fast, with the numbers measured along the way.

The bot is one C++ file of about 900 lines. It has four parts, and this page follows them in the order the data flows:

The rules that matter

Two players, up to four snakes each, on a side-view grid of platforms. Every snake moves one cell per turn, all at once, and gravity pulls down any snake that rests on nothing. The longest total body wins. Several rules are only visible in the referee's Java source, and the simulator has to get every one of them right:

  • Order within a turn: all moves, then eats, then beheadings, then falls.
  • The tail moves first. A cell a tail just left is free, unless that snake ate this turn (then the tail stays).
  • Eating comes before beheading. Two heads entering the same apple both grow, then both lose their head.
  • Three parts or fewer (counted with the new head) and a collision removes the whole snake. A longer one only loses the head.
  • The facing is not stored. It is head minus neck, recomputed every turn. A backward command is ignored.
  • Outside the grid is empty space, not wall. A snake dies out there only when every part is at y ≥ height + 1, and only right after a fall step.
  • Ties are broken by "losses", the parts lost to beheadings and collision deaths.

Board: a 64 × 48 byte array

The grid is at most 44 × 24, but snakes may hang off its edges, so the model adds room around it: 10 columns left, 8 rows on top, and the rest to the right and below. One byte per cell.

ValueNameMeaning
0EMPTYfree
1APPLEpower source: solid for falls, eaten by a head
2WALLplatform
3VOIDedge of the model: a head that enters it is beheaded, nothing rests on it
4 + iSNAKE + ia body part of snake i

The order of the values is chosen so the two hot tests are one comparison each:

occ[c] >= WALL      // a head here collides: wall, void or any body
occ[c] <  WALL      // free to enter: empty or apple
Why a ring of VOID. With it, no move and no fall ever needs a bounds check: any step off the model lands on a cell that already says "stop". It is the one place the model differs from the game, where a snake could wander more than 9 columns outside the grid. The search never wants to, and no opponent has in a checked game.

Snake and state

struct Snake: a ring buffer

struct Snake {
    uint16_t b[128];              // cells; b[h] is the head
    uint8_t h, len, alive, sup;   // sup: parts with a wall or an apple right below
    uint8_t f;                    // facing: 0 up, 1 right, 2 down, 3 left
    int head()      { return b[h]; }
    int part(int i) { return b[(h - i) & 127]; }        // 0 = head
    int tail()      { return b[(h - len + 1) & 127]; }
};

The facing f is cached instead of recomputed from head minus neck on every selection. It is written when a head advances. A beheaded snake does not advance, so it keeps the old value, which is exactly "old head minus old neck": the referee's rule, for free.

struct State

struct State {
    uint8_t occ[3072];     // the board
    Snake s[8];            // player 0's snakes first, then player 1's
    int napples, turn;
    int losses[2];         // the tie-break
    int len[2], alive[2];  // total body parts and live snakes per player
};                         // 5,200 bytes

len, alive and napples are updated in place by every move, so the end-of-game test and the score cost nothing:

bool terminal() { return napples == 0 || alive[0] == 0 || alive[1] == 0 || turn >= 200; }

A whole state is copied once per search iteration. At 5.2 kB that copy is 1–2% of the search time, so the state was kept simple instead of adding undo logic.

One turn: State::step

Three passes over the snakes, in the referee's order.

Pass 1: move, and release the tail

for each live snake i:
    nh[i]  = head + DELTA[mv[i]];
    eat[i] = occ[nh[i]] == APPLE;
    if (!eat[i]) {
        t = tail;
        sup -= (occ[t + 64] is WALL or APPLE);   // the tail was resting on something
        occ[t] = EMPTY;  len--;
    }

Tails are cleared before any collision test. That one ordering gives the rule "a cell a tail just left is free" with no special case, including a snake chasing its own tail.

Pass 2: who collides

col[i] = occ[nh[i]] >= WALL;                     // wall, void, any body (own included)
for j != i:  if (nh[j] == nh[i]) col[i] = true;   // two heads, same cell

All collisions are decided on the same picture of the board, before any new head is written, because the referee resolves them simultaneously. Other snakes' old heads are still in occ: they are necks now, and still solid.

Pass 3: apply

if (!col[i]) {                       // normal move
    h = (h + 1) & 127;  b[h] = nh[i];  f = mv[i];  len++;
    occ[nh[i]] = SNAKE + i;
    if (eat[i]) napples--, len[owner]++, unsupport(nh[i]);
    sup += (occ[nh[i] + 64] is WALL or APPLE);
} else {
    if (occ[nh[i]] == APPLE) remove the apple;        // eaten by every head on it
    size = len + 1;                                  // with the new head
    if (size <= 3) die: clear the body, losses += size;
    else           behead: losses += 1;             // nothing to undo: the head was never written
}
The beheading costs nothing. The new head is only written for snakes that survive. A beheaded snake "moved forward and lost its head", which leaves it exactly where pass 1 left it: the old body, one tail cell shorter.

Falls

The referee's rule: a snake is grounded if any part is directly above a wall, an apple or a grounded snake. Every other snake drops one row, together, and the test repeats. That loop is in the source as falls(), kept as the reference. It was 47% of the search time, because falling is not rare: a snake climbing straight up falls back one row every single turn.

Trick 1: support counters

sup counts the parts of a snake that have a wall or an apple directly below. Three events change it, and step handles all three as it goes:

  • the tail leaves a cell above a wall or apple: −1
  • the head arrives above one: +1
  • an apple is eaten: the part sitting on it, of whichever snake, loses its support (unsupport): −1
unsigned air = 0;
for each live snake i:  if (!s[i].sup) air |= 1 << i;
if (air) fastFalls(air);        // usually skipped for most snakes

If every snake has sup > 0, nothing can fall and the turn is done. Otherwise only the snakes in air are looked at.

Trick 2: fastFalls, drop straight to the landing row

Snakes in the air fall in lockstep, so they never block one another. That means the drop of one airborne snake is simply the distance to the first cell, under any of its parts, that is neither empty nor part of another airborne snake.

for (;;) {
    for each snake i in air:
        d[i] = min over its parts of (free cells straight below);
               // a part with its own body right below is skipped: the lower part decides
        if (d[i] == 0) { air -= i;  restart; }   // rests on a grounded snake: it is ground now
        lim[i] = rows until all of it is below the grid;
    m = smallest d[i] or lim[i];
    clear all airborne snakes from occ;
    shift each by m rows;   those with lim[i] == m are out of the game;
    write them back;
    those with d[i] == m have landed: recount sup, air -= i;
    if (!air) return;
}

Compared with the reference loop, which rescans all eight snakes for every single row of every fall, this touches only the airborne snakes and usually runs once.

Why "restart" on a drop of 0. A snake resting on a snake that is itself in the air must fall with it. A snake resting on a grounded one is grounded. Removing it from air changes what counts as transparent for the others, so they are measured again.

Proving it exact

Fast code against reference code

Build the bot and the referee twice, once with -DSLOWFALL (the referee's loop, no shortcuts). With a fixed number of iterations and fixed seeds the search is deterministic, so both builds must play the same games move for move. 80 games with 8 snakes each: identical results. The same test covered the support counters and the cached facing.

The simulator against CodinGame: resync

The input never says what the opponent played. Each turn the bot takes the previous position, its own moves, and tries every combination of opponent moves, three per snake, at most 81:

for each combination c:
    State t = prevS;
    t.step(my moves + combination c);
    if (sameState(t, cur)) {             // every body, cell for cell, and the apple count
        cur.losses = t.losses;           // losses are not in the input either
        playedMv = these moves;
        return true;
    }
return false;                            // the simulator disagrees with the game

One pass does three jobs: it proves the simulator matched the referee on that turn, it recovers the opponent's moves, and it carries the tie-break counters forward. A failure is counted in stderr and tagged DS on a move, which shows in arena battle logs where stderr is not kept. Result so far: 0 failures.

Search: Smitsimax

Eight snakes moving at once is 3⁸ = 6,561 joint moves per turn, too many for a normal tree. Smitsimax gives each snake its own tree over its own moves and runs them all in one shared simulation.

struct Node

struct Node {
    float   w[4];    // sum of values per move, from my point of view
    float   n[4];    // visits per move; float so SSE can load it directly
    int32_t ch[4];   // child node per move, 0 = none yet
    int32_t N;       // visits of this node
};                   // 52 bytes, in one array of 1.5M allocated once

Nodes come from a bump allocator (newNode: clear 52 bytes, return the next index). The pool is not cleared between turns: resetting the counter to 1 is the whole "free". Index 0 means "no node".

validMask: prune suicide

For the snake's three non-backward directions, a move is kept if the target cell is empty or an apple, or if it is the tail of some snake (which will have moved away). If nothing is left, the snake goes straight. Without this, random moves into walls drown the statistics, as one mid-Legend post-mortem reported.

selectMove: UCB with no branches

The formula per move is q = ±w/n + C·sqrt(ln N / n), with the sign flipped for the opponent's snakes. Written as a loop with ifs it was 42% of the search time on CodinGame: the branches depend on random data and mispredict. The x86 version computes all four moves at once and has no data-dependent branch:

e = C * sqrtLog[N];                              // sqrt(ln N) from a table of 65,536 floats
n = load(nd.n);
q = load(nd.w) * sign * rcp(n)  +  e * rsqrt(n);    // SSE approximate 1/n and 1/sqrt(n)
q = blend(q, 1e6 + random byte, n == 0);         // unvisited: huge, in random order
q = blend(-1e9, q, maskTab[mask]);               // not a valid move: never
m = horizontal max of q;
return ctz(movemask(q == m));                    // position of the maximum
  • rcp and rsqrt are the 12-bit approximate instructions: about 4 cycles each instead of ~15–20 for a division or a square root, and UCB does not need more precision.
  • Unvisited moves get 10⁶ plus a random byte, so they win against any visited move and tie-break randomly, with no separate "expand" code path.
  • maskTab is a 16-entry table of ready-made SSE masks, indexed by the 4-bit valid-move mask.

After the change selection is 24–31% of the time. ARM builds (the local Mac) use the plain loop with the same logic.

The loop: search

for (;;) {
    every 16 iterations: stop if the clock passed the budget;
    depth = 3 + iters/250   (first 1000 iterations)   then +1 per 1000;
    State S = root;                                   // the 5.2 kB copy
    for (d = 0; d < depth && !S.terminal(); d++) {
        for each live snake i:
            mask = validMask(S, i);
            m    = selectMove(pool[cur[i]], mask, sign of owner);
            remember (cur[i], m);
            cur[i] = child of cur[i] by m, created if missing;
        S.step(all moves);
        sum += length difference;                     // for the "eat sooner" term
    }
    raw = evaluate(S, ...);                           // once, at the end
    for every remembered (node, m) of snake i:  w[m] += val[i];  n[m]++;  N++;
}
play, for each of my snakes, the most visited move at its root;
  • Progressive depth. The first iterations are shallow (depth 3), so every snake's first moves get sampled before anything deep is tried. By the end of a turn the depth is 11–14. The idea is from _H3R0_'s post-mortem.
  • The clock is read every 16 iterations, not every one: reading it costs about as much as a quarter of an iteration.
  • Budget. 44 ms counted from the first input line of the turn, 850 ms on the first turn.

Evaluation

evaluate returns one number from my side, raw, in units of "apples":

TermWeightWhy
length difference1the score. Half from the final position, half from the mean along the simulated line, so the same apple eaten sooner is worth more
apple ownership0.25 / apple+ if my nearest head is closer than theirs, − if further. Removing it costs 100 Elo
distance to the nearest reachable apple, per snake≤ 0.940.08 per cell for the first 8 cells, 0.015 for the next 20, then flat
losses difference0.05the tie-break
head elevation0.01 / rowhigher is slightly better
finished game± 4added to the length difference, by score then losses
The distance cost must stay below one apple. When a snake eats the last apple it can reach, its "nearest apple" jumps to something far away or out of reach. If that jump costs more than the apple was worth, the evaluation goes down for eating, and the snake refuses to eat. Larger distance weights lost for exactly this reason (−89 Elo at 0.2 per cell) until the cost was capped at 0.94.

Gravity-aware distances

Board dumps of lost games showed the real problem with v1.0: the snakes sat still. Most apples hang in the air, a snake of length 3 cannot reach one four rows up, and a plain shortest-path distance pointed straight at it. The opponent ate 19 apples in the first 24 turns; we ate 12.

The model that works is static. After every turn some part of a snake rests on something, so its head is never more than (length − 1) cells of free path from a supported cell, a free cell with a wall or an apple below it. Two passes on turn 1:

  1. bfsSupport: one multi-source BFS from every supported cell gives hsup[c], how far cell c is from support.
  2. bfsGravity: for each apple and each length b from 1 to 16, a BFS from the apple that only walks through cells with hsup ≤ b − 1. Result: gdist[apple][b−1][cell], one byte, 255 = out of reach at that length.

A first model, "never fall: every unsupported run along the path must be shorter than the body", lost 73 Elo and, with a strong penalty, 382. It is wrong about the game: a snake that turns sideways at the top of its column drops one row and carries on. Falling is part of normal movement.

Per-snake credit

The largest single gain. In plain Smitsimax every tree receives the same value. But that value mostly reflects what the other seven snakes happened to do in that simulation, so each tree is learning from noise.

own[i] = (length of snake i now − at the root) − its distance cost;

val[i] = squash((raw ± own[i]) / 6);     // + for my snakes, − for theirs (they minimise)
...
node.w[m] += val[i];                      // each tree gets its own snake's value

Every snake still sees the shared result, plus an extra share of what it did itself. Measured against the same bot without it:

Weight of own[i]0.5124
Elo vs weight 0 (100 games each, ± 75–95)+269+288+205+173

squash is a rational approximation of tanh (x(27+x²)/(27+9x²), clamped at ±3). Eight values per iteration made the real tanh worth replacing.

Protocol and resync: main

  1. Init. Read the grid into baseOcc (walls plus the VOID ring), the snake ids and owners. Allocate the node pools and fill the sqrtLog and maskTab tables.
  2. Each turn. Start the clock at the first input line. Rebuild cur from scratch: copy baseOcc, place apples, parse each body string straight into its ring buffer. Parts outside the model are cut off.
  3. Turn 1 only. Record the apple cells and run bfsSupport, then bfsApple and bfsGravity per apple.
  4. recount. Totals per player, sup and facing of every snake.
  5. resync. Check the simulator against the game and recover the opponent's moves (above).
  6. search with what is left of the 44 ms, then print id DIRECTION for each of my live snakes, joined by ;.
  7. Remember the position and my moves for the next turn's resync.

The state is rebuilt from the input every turn instead of trusting the simulated one. The simulated state is only used to verify, so one bad turn can never corrupt the rest of the game.

How much is speed worth? Measured: three times the iterations is +104 Elo at 1,000 iterations per move and +63 at 4,000. At the arena's 6,000–8,000 that makes a 1.5× faster engine worth about +20. The 27% speed-up alone, tested in real time against v1.0, was −14 ± 61: nothing measurable. For scale, the per-snake credit, six lines of code, was +288. Reported figures from other players: about 50k turns per 50 ms for the contest winner, 4k–6k iterations per 45 ms for sZoom. This engine is in that range; the "150k / 250k simulations" quoted in two post-mortems are probably counted per snake move, which would put this one near 400k.

Local tools in the same file

PARAM(name, default)
Every constant of the search and evaluation. In a -DLOCAL build it reads SB_name from the environment, so a parameter sweep needs no rebuild. In the submission it is a plain constant.
SB_ITERS=N
Replace the clock by a fixed number of iterations per move. With SB_SEED the bot is deterministic, which is what makes the exactness test and load-independent matches possible.
SB_BENCH=N
Play 100 turns of self-play from the given position at N iterations and print simulated turns per second, with the phase split in a -DPROF build.
-DPROF
The phase profiler: PROF_START / PROF_END(phase) around copy, selection, move, fall, evaluation and backup. Works on CodinGame by putting #define PROF on the first line.
-DDUMP=N
Print the board to stderr every N turns. This is what showed the snakes sitting still.
-DSLOWFALL
Use the referee's fall loop as written: the reference build.

tools/referee.cpp includes bot.cpp for the rules, adds a port of the official map generator (GridMaker.java: mirrored walls, filled air pockets, thinned walls, sunk bottom island, apples, spawns) and runs two bot processes over pipes, every map with both seats. build/bot@SB_UCB_C=0.4 gives one side its own parameters. The same matches run on Kaggle CPU kernels through tools/kaggle_match.py.
